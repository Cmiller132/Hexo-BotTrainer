# Adversarial reviews

## PARITY — outputs within fp16 tol of the current forward on identical inputs (bias index, masking, softmax, head_dim padding, fp16 accumulation, decode).
verdict: fix-then-ship | parity: yes

- NON-BLOCKING for fp16 parity, but FLAGGED: the flex fallback (hexflash.py flex_attention_relpos) uses mask_mod returning live[b,kv_idx] -> pad keys get -inf, whereas the oracle (model.py:329 build_attn_bias) uses additive +PAD_KEY_MASK_VALUE=-3.0e4 (finite). Both drive pad-key softmax weight to exactly 0 because token keys (slots<8) are never masked (trunk seq_mask=cat([ones(b,8),mask])), so no all-masked row and no 0/0. Parity holds within fp16 — but ONLY because of the token-key invariant; the flex path has NO defense if that invariant is ever broken (e.g. a future change masking a token key would give NaN under -inf vs 0/0 under -3e4). Add an explicit assertion that seq_mask[:, :NUM_TOKENS] is all-True before the flex/hexflash call.
- VERIFY-AT-PAUSE (cannot confirm statically): hexflash.py _hexflash_kernel references HEAD_DIM_CONST (module global) and HEAD_DIM_CONST=HEAD_DIM is defined AFTER the @triton.jit kernel in the file. Triton resolves free globals at first-call JIT trace, not at def time, so this likely works, but the ordering is fragile and untested. If Triton captures globals at decoration it will NameError. Pass HEAD_DIM as a tl.constexpr kernel arg instead of relying on global closure — removes the only execution-time unknown in the head_dim-24-lane mask that the whole 24->32 zero-pad exactness depends on.

## CORRECTNESS: pad-inertness, token-vs-cell sequence handling, legal-prefix prior layout, terminal/empty rows, cu_seqlens/offsets consistency, Rust<->Python ABI byte contract.
verdict: fix-then-ship | parity: uncertain

- [bias-module / hexflash kernel] PAD-QUERY ROW NaN POISONS LIVE OUTPUT VIA LayerNorm — NOT inert. The spec repeatedly claims pad-query rows 'may compute garbage' because AttnBlock re-zeros with `*m` (model.py:193). That argument is FALSE for the hexflash kernel as written. A pad-query row (offs_m >= NUM_TOKENS+n, i.e. mask False) attends over the SAME key set as live rows. Its q is zero-loaded (pad feats are 0 -> q_proj(0)=bias, finite), so it does NOT produce NaN by itself — but the real hazard is the reverse: the kernel output for pad-query rows is FINITE garbage, multiplied by m=0 in AttnBlock => 0. That part is fine. HOWEVER the genuinely broken case is a query row (live OR pad) whose ENTIRE attended key set within a BLOCK_N tile is -inf AND no live key exists earlier. Re-examine: token keys (slots 0-7) are always live, so the first tile is never all -inf. Confirmed safe. The ACTUAL blocker is different — see next.
- [bias-module / hexflash kernel] tl.dot WITH BLOCK_D=32 AND head_dim 24: the kernel zero-loads q/k lanes 24..31 via `d_live = offs_d < HEAD_DIM_CONST`. But `HEAD_DIM_CONST` is referenced INSIDE the @triton.jit kernel as a Python module global, NOT passed as a tl.constexpr parameter. Triton jit closures capture module globals at first-trace, but `HEAD_DIM_CONST` is defined in the module AFTER the kernel function in the deliverable text ('HEAD_DIM injected as a module-level constexpr' appears below _hexflash_kernel). If the import/definition order leaves it unresolved at trace time it is a NameError at compile; if resolved it is a non-constexpr int used in a comparison producing a tensor mask — workable, but it MUST be a tl.constexpr for the mask to be compile-time. This needs the GPU pause to confirm it even compiles; flagged as build-risk, not silent-wrong.
- [evaluator-packing vs rust-abi] V2 ABI WIRE CONTRACT IS INCONSISTENT BETWEEN THE TWO COMPONENTS — payloads will KeyError or mis-decode. rust-abi emits keys `node_coords`(i32), `gather_index`(i32, 7-wide, tap0=self), `cu_seqlens`, and ALSO `node_qr`/`nbr` only on the v1 path (NOT v2). evaluator-packing's `_parse_v2` reads `node_coords`, `cu_seqlens`, `legal_counts`, and `nbr_local`/`nbr` (6-wide) — it does NOT read `gather_index` and instead rebuilds `self_idx`+remaps `nbr` itself. So rust-abi ships a fused 7-wide `gather_index` that evaluator-packing never consumes, and evaluator-packing expects a 6-wide `nbr`/`nbr_local` that rust-abi does NOT emit on the v2 path. This is a hard mismatch: a v2 flush would raise (missing `nbr`) or silently use the wrong buffer. The fallback-compat `_v2_fields_present` checks for yet a THIRD set of names (`v2_node_feats`, `v2_coords`, `v2_gather_idx`, ...) that NEITHER other component emits — so v2 is in practice never activated through that path, masking the bug but proving the three components were written against three different field-name contracts. BLOCKER for any v2 enablement; harmless only because v2 defaults off.
- [rust-abi] V2 node_coords WIDTH MISMATCH vs Python int64 expectation in the dense scatter. rust-abi emits `node_coords` as i32. evaluator-packing `_parse_v2` does `np.frombuffer(payload['node_coords'], dtype=np.int32)` then stores as `qr` and later `np_coords = np.zeros(..., dtype=coords_dtype)` where coords_dtype is int64 for sdpa / int32 for kernels. For the SDPA fallback on a v2 payload it up-casts i32->i64 — fine. But the model's `build_attn_bias` indexes `_exact_lut[(clamped_q*17+clamped_r)]` with these coords; that path requires int64 indexing and the cast is present, so OK. Not a blocker by itself, but only because of the int64 cast in the pack loop. Flag: if anyone 'optimizes' away that cast (the comments invite skipping the dense scatter for ragged-direct), the i32 coords would break long-indexing of _exact_lut.
- [parity-tests] _make_payload nbr sentinel mapping uses a dead `if False else` ternary AND references `C.NBR_SENTINEL_U16` which exists (constants.py:35) but the branch is unreachable; the live branch hardcodes 0xFFFF. Cosmetic/self-flagged, not a correctness blocker, but the test author already noted it — confirms the suite was not run end-to-end.

## PERFORMANCE — will it actually beat the deployed baseline across the shape mix; where does it regress?
verdict: fix-then-ship | parity: uncertain

- LARGE-S SPEEDUP CLAIM IS LIKELY INVERTED — hexflash probably REGRESSES the band it targets. I recomputed the Amdahl share from the actual model (model.py: C=96, H=4, Dh=24, trunk = stem + 6 ConvBlocks(2 convs each) + 3 AttnBlocks + 2 policy convs). Per-token S-LINEAR work (all HexNodeConv at 7*C*C plus the 3 blocks' QKV/out/MLP) = 1,188,864 MACs. The attention S-QUADRATIC part hexflash touches (3 blocks * 2 * H*S*Dh) is only 3.4% of total at Npad=64, 30.6% at 900, 46.7% at 1800, 61.6% at 3300. That share is the FLOP CEILING assuming hexflash drove attention to ZERO. But hexflash does the opposite: it pads head_dim 24->32 (+33% attention MACs, the spec's own attention-kernel COMPONENT admits this) AND replaces a deliberately-fast fused SDPA mem-efficient kernel (model.py:317-331 steers SDPA onto the fp16 mem-efficient backend on purpose) with a hand Triton FA2 that on a 4070Ti realistically lands at 0.5-0.7x of SDPA throughput. Net end-to-end vs baseline: at Npad=900 ~0.78-0.91x, at 1800 ~0.70-0.87x, at 3300 ~0.64-0.83x. Even the BEST case (hexflash matching SDPA util exactly, k=1.0) is ~0.83-0.91x because of the +33% head-pad tax alone. The spec's '~1.2-1.5x large-S' is not supported by the compute structure; it is a REGRESSION risk on the exact band it targets.
- THE '~70% bias machinery' JUSTIFICATION DOES NOT TRANSFER TO LARGE-S. That 70% (inference.py:71-73) is a SMALL-S, launch-bound, kernel-COUNT figure (many tiny gather/elementwise kernels). hexflash's one genuine S-quadratic win is eliminating the one-time (B,4,S,S) build_attn_bias materialize (model.py:262-331, called once at model.py:350, shared across all 3 blocks). I quantified it: the bias-build S^2 traffic coefficient (~5*H=20) is ~29x SMALLER than the attention-matmul S^2 coefficient (3*2*H*Dh=576) it must redo. So removing the bias transient saves ~1/29th of the quadratic cost while the kernel swap pays the +33% pad and any util gap on the other 28/29ths. The spec carries a small-S profiling number into a large-S argument without re-deriving it.
- VRAM-HEADROOM -> higher PAIR_CEILING is the only solid win, and it is left unquantified. Eliminating the (B,4,S,S) fp16 bias transient (the thing PAIR_CEILING=3.8e7 at inference.py:26 exists to bound) genuinely frees VRAM and could let batches grow, which raises throughput via larger flushes — orthogonal to the kernel speed. This is the rewrite's REAL performance lever, yet the spec lists it as item 5 'measure, don't assume' rather than the headline. The bench harness (benchmark COMPONENT) does measure peak VRAM, good — but no design states the expected ceiling-raise or the resulting flush-size/throughput delta, so there is no acceptance target.

## RUST/ABI SAFETY — memory safety, lifetimes, new buffers, pinned/zero-copy claims, GIL handling, cache correctness, Rust↔Python ABI consistency
verdict: fix-then-ship | parity: uncertain

- PINNED-BUFFER LIFETIME IS UNSOUND FOR DEPTH>=2 (rust-serveloop + evaluator-packing). The serveloop component's own §4.1 admits the hazard but the delivered code does NOT resolve it, and the Python half makes it concretely a use-after-the-DMA-reads-freed-host-memory bug. In the live inference.py:243-249 every H2D buffer is `t.pin_memory().to(device, non_blocking=True)`. `t.pin_memory()` returns a NEW temporary pinned tensor that is dropped at the end of `_forward_group` (Python has no reference to it after the call). With a SINGLE D2H sync inside `result()` this is safe ONLY because the live depth-1 path calls submit then immediately result before the next flush. The proposed depth-2 ring holds the `PendingEval`/handle across ANOTHER full select pass AND another submit — but the pinned SOURCE staging for flush k is the per-call temporary that was already dropped/reused. The serveloop claims `PendingEval` 'owns the handle (Py<PyAny>) which keeps the async H2D buffer alive' — that is FALSE for the current evaluator: the handle holds GPU output tensors (values_gpu/priors_gpu), not the pinned HOST input staging, and the non_blocking H2D reads the host buffer asynchronously. Nothing in the delivered Python keeps the pinned host source alive past the submit_payload return. Depth-2 therefore DMAs from freed/reused pinned memory → silent data corruption, not a crash. The evaluator-packing component never added a pinned-staging pool keyed by pipeline slot, so the contract the serveloop depends on does not exist. MUST ship depth=1 until the evaluator owns a depth-N pinned staging pool whose buffers are referenced by the handle.
- RUST UNIT TESTS DO NOT COMPILE — WRONG ENGINE API (rust-abi). The three delivered #[cfg(test)] tests (gather_index_layout_matches_model, v2_gather_reduces_to_v1_neighbours, cu_seqlens_equals_v1_offsets) call `state.is_legal_placement(coord)` and `state.apply_placement(coord)` as METHODS returning bool/(). Ground truth (hexo_engine): `is_legal_placement` is a FREE fn `rules::is_legal_placement(&HexoState, HexCoord) -> Result<(), MoveError>` (rules.rs:11) and `apply_placement` is a FREE fn returning a Result (state.rs:399). `RustHexoState::new()` exists (state.rs:151) but the placement calls are wrong. These are the EXACT 'most load-bearing test in the v2 path' (the gather-index off-by-one pin) the component named — and they will not build, so the static gather-layout certification the whole 'no silent conv-neighbour corruption' claim rests on does not actually run. The component flagged this uncertainty itself; it is real and blocking for that test file.

## INTEGRATION — do the 10 components' interfaces actually match, with no contradictions between attention / packing / ABI / serve-loop / fallback pieces?
verdict: fix-then-ship | parity: uncertain

- V2 ABI FIELD-NAME SCHISM (3 components disagree on the same wire). The rust-abi component (build_chunk_payload_v2) sets keys: 'node_feats','node_coords','gather_index','gather_width','gather_sentinel','cu_seqlens','legal_counts'. The evaluator-packing component (_parse_v2) reads: 'node_feats','node_coords','cu_seqlens','legal_counts' AND nbr via payload.get('nbr_local', payload.get('nbr')) — it NEVER reads 'gather_index', and Rust NEVER sends 'nbr_local' or 'nbr' on the v2 path. So _parse_v2 against the actual Rust v2 payload throws (nbr_buf=None -> np.frombuffer(None)). Meanwhile the fallback-compat component (_v2_fields_present) gates on a THIRD namespace entirely: 'v2_node_feats','v2_coords','v2_gather_idx','v2_cu_seqlens','v2_legal_counts' — none of which Rust emits, so use_v2 is ALWAYS False and the v2 path is dead even when Rust sends abi=2. Three components, three field schemas. Must converge on one frozen key list before assembly.
- GATHER-INDEX REPRESENTATION CONTRADICTION (the core §C3 disagreement, self-admitted by rust-abi). The spec §C3 froze 'flat int32 gather-index (tap0=self + 6 nbr already remapped sentinel->pad-row)'. The rust-abi component deliberately BROKE that contract: it ships gather_index node-local with sentinel PRESERVED (GATHER_SENTINEL=-1), arguing plan_groups owns pad_to. But the trunk-conv component's HexfieldNet.trunk STILL builds gather_idx itself (self_idx=arange + cat([self_idx, nbr]), unchanged from live model.py:346-347) and consumes a 6-wide 'nbr' tensor, NOT a 7-wide precomputed gather index. So nobody consumes Rust's 7-wide gather_index: trunk wants nbr(6), evaluator-packing's _parse_v2 wants nbr(6) too. Rust's entire gather_index/gather_width/gather_sentinel emission is unconsumed dead weight, and the 6-wide nbr the consumers need is NOT emitted on the v2 path. Either Rust must emit a 6-wide int32 'nbr' on v2 (drop the 7-wide gather_index), or trunk+evaluator must be rewritten to consume the 7-wide index. Currently neither side meets the other.
- DUPLICATE / CONFLICTING _forward_group and submit_payload OWNERSHIP. The evaluator-packing component delivers a FULL rewrite of submit_payload/_forward_group with signature _forward_group(self, src, legal_counts, start, end, pad_to, ...) reading from a 'src' bundle dict. The fallback-compat component delivers DIFF patches against the LIVE _forward_group whose signature is _forward_group(self, feats, qr, nbr, offsets, sizes, legal_counts, ...) (positional fields, inference.py:206) and against the LIVE submit_payload (the abi!=1 hard-reject at inference.py:134). These two patch the SAME two methods with incompatible base assumptions: fallback-compat's '_run_forward' helper, 'self._sc', 'self._uses_new_attn', 'group_impl' routing must be merged INTO evaluator-packing's rewrite, but evaluator-packing already wrote its own per-group impl routing (_select_impl/_ensure_impl) with DIFFERENT semantics (no fallback/degrade, no strict mode, no set_attention_impl restore-in-finally). Assembling both as written = two competing impl-routing mechanisms in one file. One must be deleted.
- ATTENTION-IMPL COORDS DTYPE: double int32 conversion + sdpa-int32 hazard. trunk-conv's trunk does kcoords = coords.to(torch.int32) internally when use_kernel. evaluator-packing ALSO sends coords as int32 from _forward_group (coords_dtype=int32 for hexflash/flex). Harmless duplicate. BUT the fallback-compat _run_forward does coords_new = d_coords.to(torch.int32) for the new path and passes original int64 d_coords to the sdpa fallback — while trunk-conv's trunk, under impl=='sdpa', calls build_attn_bias(coords,...) which at model.py:278 indexes _exact_lut with (clamped_q*17+clamped_r); int32 coords there are fine, but the live evaluator sends int64 and the parity claim 'sdpa path byte-identical' depends on int64. With three independent places deciding coords dtype (trunk, evaluator-packing, fallback), the dtype that actually reaches build_attn_bias on a degraded large-S group is ambiguous. Pin one owner.
- set_attention_impl IS GLOBAL, but routing is PER-GROUP across THREE owners with different restore policies. set_attention_impl (model.py:256) flips impl on ALL 3 attn_blocks (process-global on the model). evaluator-packing's _ensure_impl flips and restores to 'sdpa' at end of submit_payload. fallback-compat's _run_forward flips and restores to self._base_attn_impl in a finally PER CALL. trunk-conv reads self.attn_blocks[0].attn.impl to decide use_kernel. If both evaluator-packing's _ensure_impl AND fallback-compat's _run_forward are present, they race on the same mutable model.attn_blocks[*].attn.impl within one flush. Compounded by the async pipeline (rust-serveloop depth-2): two flushes in flight can interleave, but the model impl is a single shared mutable flag — a depth-2 large+small interleave could run a small-S group under a leaked hexflash impl. The submit/finish split means the forward for flush k+1 may be enqueued while flush k's is not drained; both went through the same model object. This needs an explicit guard that impl flips happen only at submit-enqueue (not across the async boundary) and that depth-2 never mixes impls mid-flush.

## COMPLETENESS — what is missing for a working build/first GPU pause
verdict: fix-then-ship | parity: uncertain

- [attention-kernel / model.py — SDPA-SCALE PARITY, the worst gap] The flex fallback is WRONG against the production path. Live `sdpa` (model.py:168) calls `F.scaled_dot_product_attention(q,k,v,attn_mask=attn_bias)` with NO explicit scale and a FULL additive bias that ALREADY contains PAD_KEY_MASK_VALUE. SDPA internally multiplies q@kᵀ by 1/sqrt(head_dim)=1/sqrt(24) and adds the mask. The flex deliverable computes `bias_val = bias_table[pair]` (the learned bias ONLY, WITHOUT the pad-key fill) and passes it via score_mod `score + bias_val[...]`, then handles pad keys via a SEPARATE mask_mod. The deliverable's own note admits this is 'numerically equivalent' but it is NOT bit-equivalent to the materialized oracle the Tier-2 gate (diff<=2e-3) compares against, AND more importantly flex's default scale is 1/sqrt(E) where E is the PADDED head dim = 32, not 24. The component claims it passes `scale=1/sqrt(24)` explicitly — that part is correct — but the combination (mask_mod pad instead of additive -3e4, bias without fill) means the flex output will differ from `materialized` (which adds the literal -3.0e4 into the softmax). Whether that lands under 2e-3 is UNVERIFIED and the spec elsewhere demands exact additive parity. This is the single most likely first-pause failure. Must: fold PAD_KEY_MASK_VALUE additively into score_mod (not mask_mod) so flex matches `materialized` exactly, or accept it can only be gated against sdpa not materialized.
- [rust-abi — TESTS DO NOT COMPILE, the whole static de-risk is void] All three #[cfg(test)] fixtures call `RustHexoState::new()`, `state.is_legal_placement(coord)`, and `state.apply_placement(coord)`. ## DEPLOY/ROLLBACK RISK — can this go live behind a flag with instant rollback without endangering the running multi-day training run or its data?
verdict: fix-then-ship | parity: uncertain

- IRREVERSIBLE DATA-MIXING (the central risk). File 4 _rewrite_supervise_main1.sh hardcodes RUNDIR=/mnt/e/Hexo-BotTrainer/runs/hexfield_main_1 — the SAME dir as the live supervisor (verified: live config output_dir + manifest.json both point there; latest live ckpt is epoch_000031.pt). The rewrite supervisor launches a FULL `hexo_train.cli.train_model` (line 74 of the live script it copies), not an inference-only process. That trainer does self-play AND TRAINING PASSES AND WRITES epoch_0000NN.pt + selfplay/ + diagnostics/eval_pool.json into the live run dir. So cutover does NOT just 'swap which forward kernel runs' — it advances the actual training: it ingests rewrite-generated self-play, runs an optimizer step, and OVERWRITES the checkpoint sequence. If a numeric defect slips past the parity gates (Tier 2/3 are GPU-pause-only and the speedup/VRAM claims are explicitly NOT statically certain), the corrupted gradient step is BAKED INTO epoch_000032.pt and the BT eval pool. _rewrite_rollback.sh (File 5) only swaps $ROOT back to the live tree and resumes from 'latest epoch_*.pt' — which is now the rewrite-produced epoch_000032.pt. Rollback restores the CODE but not the WEIGHTS/DATA. This contradicts the runbook's own claim 'the rewrite never changed weights... checkpoints are interchangeable' — true only for a pure-inference process, false for the training supervisor it actually launches. The mission is an INFERENCE rewrite; running it through the training loop on the live run dir is an unbounded, irreversible data-risk.
- NO CHECKPOINT BACKUP BEFORE CUTOVER. The runbook resumes-in-place from epoch_000031.pt and the trainer writes epoch_000032.pt into the same checkpoints/ dir. There is no step that copies the last-known-good live checkpoint (epoch_000031.pt) + eval_pool.json to a safe location before the rewrite trainer runs. If the rewrite trainer corrupts state, partially writes a checkpoint (crash mid-save), or the breaker trips after a bad epoch, the clean resume point can be lost/overwritten. _rewrite_preflight.sh only RECORDS the path of the latest ckpt (echoes it); it does not COPY it. Irreversible on any write failure.
- SHARED RUN-DIR LOCK = NO REAL CONCURRENCY GUARD ACROSS TREES, AND ROLLBACK CAN DOUBLE-LAUNCH. Both supervisors use the same supervisor.lock path, so they can't run simultaneously — good — BUT _rewrite_rollback.sh does `rm -f supervisor.lock` then `nohup` the live supervisor WITHOUT re-checking that the rewrite trainer (driver.pid) is actually dead first in all paths: it SIGTERMs driver.pid with a 20s wait then SIGKILL, but if the rewrite supervisor's EXIT trap already removed the lock and a race leaves a trainer holding the GPU, the live supervisor relaunches a second trainer → two processes contend for the 12GB GPU (run already at ~11.9/12.3 GiB per the live script comment) → OOM crash of BOTH, and the live breaker counts it. Lock removal before confirming GPU-free is unsafe on a saturated card.
